2. ABSOLUTE PRODUCT PRINCIPLES

These rules override convenience.

Principle 1 — Human first

AI amplifies K’Osez teachers and human connection.

AI must never make the product feel like humans have been removed.

Principle 2 — Real-world language

Prioritise speaking and real-world action over repetitive in-app exercises.

Principle 3 — Adult sophistication

No childish gamification.

No cartoon mascots.

No excessive badges.

No noisy gradients.

No generic SaaS dashboard aesthetic.

Principle 4 — Progress must be understandable

The learner must always understand:

- where they are
- why they are there
- what they have accomplished
- what they need to do next

Principle 5 — BLOSSOM is everywhere

BLOSSOM is not merely a screen.

It is the product's mental model.

6. BLOSSOM PLANT ENGINE

Implement the five authoritative stages:

Seed
→ Growing
→ Flourishing
→ Blossoming
→ Independent

The plant is a deterministic representation of server-side learner state.

The client must never calculate authoritative points.

Server:

activity log
→ stage engine
→ journey state

Client:

journey state
→ visual representation

Plant changes must be deterministic.

Do not use random plant states.

The learner must be able to tap the plant and see:

- current stage
- points
- qualifying actions
- progress toward next stage
- remaining requirements

Example:

Growing

42 / 60 points

8 / 8 Missions ✓

1 / 2 Speak sessions

0 / 1 Pron’Lab

Keep going — you're close to Flourishing.

---

7. ACTIVITY LOG IS THE SOURCE OF TRUTH

Every qualifying activity must generate an immutable activity event.

Examples:

MISSION_COMPLETED
SPEAK_COMPLETED
PRONLAB_COMPLETED
CLASS_ATTENDED
EVENT_ATTENDED
REAL_WORLD_BONUS

The stage engine derives progression from activity data.

Never directly increment:

"journey.points"

without an auditable activity record.

Teacher/admin overrides must generate explicit audit records.

---

8. DAILY MISSION ENGINE

Missions are one of the most important product features.

A mission must:

- require speaking
- happen in the real world
- take approximately 2–10 minutes
- fit the learner's level
- fit the learner's interests
- align with their goal
- be achievable today

Examples:

"Ask a colleague what they recommend for lunch."

"Describe your morning to someone."

"Record a 60-second explanation of what you did yesterday."

"Ask for directions without switching to French."

The mission interface should make the learner want to ACT.

Not study.

---

9. AI MISSION FEEDBACK

Pipeline:

voice recording
→ secure upload
→ speech-to-text
→ feedback engine
→ structured result
→ learner

Feedback must contain:

1. genuine strength
2. one actionable improvement
3. short model phrase

Never overwhelm the learner with corrections.

Communication success comes before perfection.

Feedback must respect CEFR level.

A1/A2:

French + target language where useful.

B1+:

Primarily target language.

10. SPEAK ROOMS

→ AI responds
→ End
→ Receive feedback

Do NOT display live translations during conversation.

11. AI PROVIDER ABSTRACTION

Never hard-code a single AI vendor throughout the application.

Create interfaces such as:

AIProvider
SpeechToTextProvider
TextToSpeechProvider
PronunciationProvider

The orchestration layer decides which implementation to use.

The mobile client must never contain provider API keys.

All AI credentials remain server-side.

AI responses must be schema validated.

Never trust raw LLM JSON.

Use structured output + runtime validation.

12. PRON'LAB

Phase 1 is intentionally basic.

The learner:

1. sees target word/phrase
2. hears model
3. records themselves
4. receives simple feedback
5. retries
6. progresses through the set

Store every attempt.

Do not over-engineer longitudinal pronunciation analytics yet.

However, design the data model so advanced analytics can be added later.

19. OFFLINE-FIRST

Offline is mandatory for the core practice loop.

Cache:

- today's mission
- next two days of missions
- Pron’Lab packs
- scenario prompts
- profile
- seven-day calendar

Offline actions are queued locally.

When connection returns:

local queue
→ API
→ server reconciliation
→ corrected client state

The server remains authoritative.

Handle:

- duplicate submissions
- expired missions
- stale catalogue items
- failed uploads
- interrupted audio uploads
- authentication expiry

gracefully.

30. DO NOT FAKE FEATURES

Never implement a feature that appears functional but is actually hardcoded.

Examples of unacceptable shortcuts:

- fake AI feedback
- fake payment confirmation
- hardcoded progress
- hardcoded plant stages
- static participant counts presented as real
- fake booking availability
- fake certificates
- fake offline support
- fake voice processing
- placeholder analytics presented as production metrics

If an external integration genuinely cannot be connected yet, isolate it behind a clean interface and clearly mark it as an integration boundary.

If YES → redesign.

Does the learner immediately understand what to do today?

If NO → redesign.

Does the plant feel meaningful?

If NO → redesign.

Does AI feel like a useful coach rather than a chatbot?

If NO → redesign.

Does the product encourage speaking in the real world?

If NO → redesign.

Does the application feel unmistakably K’Osez?

If NO → redesign.

Would a premium language centre proudly put this in front of its customers?

If NO → do not ship.
